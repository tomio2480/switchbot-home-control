# 📝 不快指数の Discord 通知で得た知見

温湿度計の不快指数を 10 分おきに計算し，Discord へ通知する機能を実装した．
その過程で得た判断を記録する．
主な内容は，電池切れの温湿度計が返す値の扱い，丸め誤差への対処，出典の選定である．

## 🧭 背景

- 常駐アプリへ，温湿度計の不快指数を監視する機能を加えた．
- 「何も感じない」「快い」以外の温湿度計を，名前付きで Discord へ通知する．
- 計算式と区分は，利用者が示した解説記事に従う．
  利用者は公的機関の発信があれば切り替えることを望んだ．

## ⚖️ 判断

### 電池切れの温湿度計を測定値なしとみなす

実機の `Meter` 2 台のうち 1 台が，電池 0・気温 0・湿度 0 を返していた．
API の応答は `statusCode: 100`（成功）であり，失敗として判別できない．
この値で計算すると不快指数は 46.3「寒い」となり，10 分ごとに誤通知が出る．

そこで次のいずれかに当たる応答を，測定値なしとして通知から除く．

- `battery` が 0 である．
- 気温と湿度がともに 0 である．

気温 0℃ 自体は実在しうるため，気温だけでは判定しない．
除外した温湿度計はイベントログへ警告として残す．
その後，同じ温湿度計が有効な値を返すことも確認した．

### 不快指数を decimal で計算する

参考記事の早見表は，値を小数第 1 位に丸めている．
`double` で計算すると，20℃・50% の 65.25 が 65.249… となりうる．
四捨五入の結果が 65.2 に変わり，表の 65.3 と一致しなくなる．

入力を `decimal` へ変換して計算し，`MidpointRounding.AwayFromZero` で丸める．
区分の判定も丸めた後の値で行い，表示と区分の食い違いを防ぐ．

### 公的機関を出典に使える範囲を限る

公的機関の発信を探したが，計算式と 8 区分を両方示すものは見つからなかった．

- 気象庁は定義と注意点を載せるが，統計の種目ではなく，式と区分を公表していない．
- 環境省の資料は暑さ指数（WBGT）と体感温度が中心である．
- 電気通信大学の早見表は，60 以上の 6 区分だけを載せている．

このため，公的機関の資料は定義と裏付けに用いた．
計算式と 60 未満の区分は，民間の解説記事だけに基づく．
README の出典表へ，用途と発信者の種別を併記した．

### 監視の失敗を周期と温湿度計の単位で閉じ込める

`BackgroundService` で例外が未処理のまま抜けると，.NET 8 の既定ではホストが止まる．
常駐アプリの Web UI まで止まるため，監視の失敗を外へ漏らさない．

- 1 台の取得失敗は，その台だけを除外して他の台の通知を続ける．
- 周期全体の失敗はイベントログへ記録し，次の周期で最初からやり直す．

当初は 1 台分の捕捉を `HttpRequestException` に限っていた．
JSON の解析失敗とタイムアウトでは周期全体が中断するため，セルフレビューで範囲を広げた．

## 🔀 代替案と棄却理由

- **応答に気温と湿度があるデバイスをすべて対象にする案** は棄却した．
  ハブや加湿器まで含まれ，依頼の「温湿度計」から外れる．
  種別の許可リスト（`Meter` 系と `WoIOSensor`）で絞った．
- **湿度 0 だけで測定値なしと判定する案** は棄却した．
  電池の値を持たない機種でも誤判定を避けるため，電池と全ゼロの 2 条件にした．
- **Webhook URL を Discord のホストだけに制限する案** は見送った．
  URL は利用者の `.env` から読む信頼された値である．
  `https` と `/api/webhooks/` の検査で入力ミスは十分に拾える．
