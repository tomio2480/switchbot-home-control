# 📝 不快指数の監視と Discord 通知で得た知見

温湿度計の不快指数を 10 分おきに計算し，Discord へ通知する機能を実装した．
その後，通知を区分の変化時だけに改め，記録・グラフ・トレイ表示を加えた．
主な内容は，測定値の扱い，丸め誤差，出典の選定，通知の判定，記録の持ち方である．

## 🧭 背景

- 常駐アプリへ，温湿度計の不快指数を監視する機能を加えた（PR #15）．
- 当初は「何も感じない」「快い」以外の間，10 分ごとに Discord へ通知した．
- 計算式と区分は，利用者が示した解説記事に従う．
  利用者は公的機関の発信があれば切り替えることを望んだ．
- 翌日，夜間に「快い」へ入って通知が止まり，利用者には故障に見えた．
  制限ではなく仕様どおりの動作だったが，過去の値を確かめる手段がなかった．
  そこで通知の方式を改め，記録とグラフ，トレイの色表示を加えた（PR #18）．

## ⚖️ 判断

### 電池切れの温湿度計を測定値なしとみなす

実機の `Meter` 2 台のうち 1 台が，電池 0・気温 0・湿度 0 を返していた．
API の応答は `statusCode: 100`（成功）であり，失敗として判別できない．
この値で計算すると不快指数は 46.3「寒い」となり，誤通知が出る．

そこで次のいずれかに当たる応答を，測定値なしとして扱う．
通知だけでなく記録からも除く．

- `battery` が 0 である．
- 気温と湿度がともに 0 である．

気温 0℃ 自体は実在しうるため，気温だけでは判定しない．
除外した温湿度計はイベントログへ警告として残す．
その後，同じ温湿度計が有効な値を返すことも確認した．

### 不快指数を decimal で計算する

参考記事の早見表は，値を小数第 1 位に丸めている．
`double` で計算すると，20℃・50% の 65.25 が 65.249… となりうる．
四捨五入の結果が 65.2 に変わり，表の 65.3 と一致しなくなる．

入力を `decimal` へ変換して計算し，`MidpointRounding.AwayFromZero` で丸める．
区分の判定も丸めた後の値で行い，表示と区分の食い違いを防ぐ．

### 公的機関を出典に使える範囲を限る

公的機関の発信を探したが，計算式と 8 区分を両方示すものは見つからなかった．

- 気象庁は定義と注意点を載せるが，統計の種目ではなく，式と区分を公表していない．
- 環境省の資料は暑さ指数（WBGT）と体感温度が中心である．
- 電気通信大学の早見表は，60 以上の 6 区分だけを載せている．

このため，公的機関の資料は定義と裏付けに用いた．
計算式と 60 未満の区分は，民間の解説記事だけに基づく．
README の出典表へ，用途と発信者の種別を併記した．
区分の色も同じ記事の体感の文字色に合わせた．

### 監視の失敗を周期と温湿度計の単位で閉じ込める

`BackgroundService` で例外が未処理のまま抜けると，.NET 8 の既定ではホストが止まる．
常駐アプリの Web UI まで止まるため，監視の失敗を外へ漏らさない．

- 1 台の取得失敗は，その台だけを除外して他の台の処理を続ける．
- 周期全体の失敗はイベントログへ記録し，次の周期で最初からやり直す．

当初は 1 台分の捕捉を `HttpRequestException` に限っていた．
JSON の解析失敗とタイムアウトでは周期全体が中断するため，セルフレビューで範囲を広げた．

一覧の取得に失敗した周期は，空の測定結果としてトレイへ渡す．
古い値を表示し続けず，灰色のアイコンで失敗を示すためである．

### 不快な間の通知から区分の変化の通知へ改める

通知が止まった原因を調べると，イベントログにエラーはなかった．
当時の値は 2 台とも「快い」で，通知しない区分に入っていただけだった．
利用回数も SwitchBot API が 1 日約 430 回（上限 10,000 回）で，制限には遠い．

「通知がない」ことが「快適」と「故障」の両方を意味していた点が問題である．
区分の変化を通知すれば，快適な区分へ戻ったことも知らせられる．
あわせて，現在の値をトレイで，過去の値をグラフで確かめられるようにした．

### 振動を 10・20・30 分前との比較で抑える

利用者が示した条件をそのまま採った．次のどちらかで通知する．

1. 30 分前と区分が違い，20 分前と 10 分前が現在と同じ．
2. 30・20・10 分前のいずれかから，区分が 2 段階以上変わった．

「n 分前」は，その時刻の前後 5 分以内で最も近い記録とする．
周期のずれや再起動で時刻が揃わなくても比べられるようにするためである．

条件 2 だけでは，急変の後 30 分間同じ通知が続く．
2 段階差が残る間，毎周期で条件を満たすためである．
そこで，最後に通知した区分と同じなら送らない条件を加えた．

さらに，条件 1 は変化の瞬間を逃すと二度と満たされない．
30 分前も現在と同じになるためである．
停止中の変化や投稿の失敗を救うため，次の場合も条件 1 を満たすとみなした．
30 分間同じ区分が続き，その区分が最後の通知と違う場合である．

### 最後に通知した区分を保存する

前項の判定は，最後に通知した区分に依存する．
メモリだけに持つと，再起動のたびに急変の通知が重複しうる．
Issue #16 でも，再起動後の状態の保持が論点に挙がっていた．

`data/notification-state.json` に温湿度計ごとの区分を保存する．
更新は投稿の成功後に限る．失敗した周期は，次の周期で前項の救済条件により再送される．
ファイルが壊れていれば空として扱う．重複が 1 回起きうるだけで，起動を止めるほどではない．

### 履歴をアプリ側で JSON Lines に記録する

SwitchBot の Open API には，温湿度の履歴を返す機能がない．
SwitchBot アプリのグラフの値も，Open API からは取得できない．
このため，グラフと通知の判定に使う値は本アプリが自ら記録する．

- `data/meter-history/` に 1 日 1 ファイルの JSON Lines で追記する．
- 記録は気温と湿度だけとし，不快指数は読み出す時点で計算する．
  計算式や丸めを直しても，過去の値に遡って反映できる．
- 書き込み途中で落ちた行は読み飛ばし，残りの記録を生かす．
- 量は 1 台あたり 1 日約 150 行で，1 年でも数 MB にとどまる．自動削除は入れていない．

Web UI のグラフは外部ライブラリを使わず，SVG を自前で描いた．
ローカルの常駐アプリであり，CDN への依存と供給網のリスクを避けたかった．

### トレイアイコンを実行時に描画する

区分の色の丸は，`Bitmap` に描いて `GetHicon` でアイコンにする．
`Icon.FromHandle` は元のハンドルを所有しないため，放置すると 10 分ごとに漏れる．
`Clone` で所有権のある複製を作り，元のハンドルは `DestroyIcon` で破棄する．
複製が元の破棄後も使えることは単体テストで確かめた．

監視はバックグラウンドのスレッドで動き，トレイは UI スレッドにある．
メニュー生成時に入る WinForms の同期コンテキストを捕まえ，更新を `Post` で渡す．

## 🔀 代替案と棄却理由

- **応答に気温と湿度があるデバイスをすべて対象にする案** は棄却した．
  ハブや加湿器まで含まれ，依頼の「温湿度計」から外れる．
  種別の許可リスト（`Meter` 系と `WoIOSensor`）で絞った．
- **湿度 0 だけで測定値なしと判定する案** は棄却した．
  電池の値を持たない機種でも誤判定を避けるため，電池と全ゼロの 2 条件にした．
- **Webhook URL を Discord のホストだけに制限する案** は見送った．
  URL は利用者の `.env` から読む信頼された値である．
  `https` と `/api/webhooks/` の検査で入力ミスは十分に拾える．
- **画面を開いたときに過去の値を API から取る案** は，API が履歴を返さないため成り立たない．
- **最後の通知を記録の再生で復元する案** は見送った．
  判定を過去へ遡って繰り返せば状態ファイルは不要になる．
  ただし判定の変更が過去の解釈まで変えるため，明示的に保存する方を選んだ．
- **記録を SQLite に持つ案** は見送った．
  書き込みは 10 分に数行で，範囲の読み出しも日付のファイル単位で足りる．
  依存を増やさず，壊れた行だけを捨てられる JSON Lines を選んだ．
